Why create_all() Is Bad In Production

Good for:

    - Learning
    - Local Development
    - Testing

Bad for:

    - Production Systems

Reasons:

    - Doesn't track history
    - Can't rollback
    - Can't alter existing schema safely
    - Doesn't support team collaboration well


What is a database migration?

    - A migration is a version-controlled change to a database schema that allows modifications without losing existing data.

What is Alembic?

     - Alembic is SQLAlchemy's official database migration tool used to manage schema evolution.

Why not use create_all() in production?

    - Because it does not track schema history, support rollbacks, or safely modify existing tables.

What does alembic upgrade head do?

    - It applies all pending migrations and updates the database to the latest schema version.

What are upgrade() and downgrade()?

    - upgrade() applies schema changes, while downgrade() reverses them.



Generate First Migration

Run:

alembic revision --autogenerate -m "initial schema"

Alembic creates:

alembic/
└── versions/
    └── xxxxx_initial_schema.py

Apply:

alembic upgrade head



Simulate Real Production Change

Management says:

Add confidence_score

Modify model:

class Prediction(Base):

    __tablename__ = "predictions"

    id: Mapped[int] = mapped_column(
        primary_key=True
    )

    machine_id: Mapped[int]

    prediction: Mapped[str]

    confidence_score: Mapped[float | None]


    Create Migration

Run:

alembic revision --autogenerate \
-m "add confidence score"

Generated file:

def upgrade():

    op.add_column(
        "predictions",
        sa.Column(
            "confidence_score",
            sa.Float(),
            nullable=True
        )
    )


def downgrade():

    op.drop_column(
        "predictions",
        "confidence_score"
    )

1] script.py.mako 

a Mako template Alembic uses to generate new migration scripts.
This template controls the default structure and content of every new migration — customizing it changes every subsequently generated revision (e.g., add headers, logging, extra imports, or standardized comments).

Under the Hood: Alembic creates a special, hidden table in your database called alembic_version. This table stores exactly one row: the hashed ID of the latest migration applied. This is how Alembic always knows exactly which version of the schema is currently active.
